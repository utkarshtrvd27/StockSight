StockSight

Next Phase Implementation Plan

From completed Gold-layer ingestion to a low-cost reporting application on Azure

Prepared: 23 August 2026

Recommended first milestone: build one end-to-end dashboard for a single stock using Gold-layer PostgreSQL data, then expand the reporting surface.

1. Current Position

StockSight already has a local Bronze, Silver, and Gold ETL flow for NSE equity data. The repository uses PostgreSQL schemas for the data layers and an elt_pipeline_orchestration.elt_config table for incremental ingestion checkpoints. The architecture diagram also shows reporting, ML, LLM, and web UI consumers of the Gold layer.

The immediate priority is to make Gold a stable reporting contract, then place a Spring Boot API between the database and a Next.js frontend.

3. Why Not Airflow or Databricks Yet?

Airflow and Databricks are strong choices at larger scale, but they add infrastructure, compute, and operational cost. For one daily NSE batch pipeline, Azure Container Apps Jobs can run the complete workflow and scale down afterward.

Revisit Airflow when there are multiple independent DAGs, complex backfills, many data sources, or a team operating pipelines. Revisit Databricks when data volume or Spark-specific workloads justify a continuously managed analytics platform.

4. Target Architecture

Local: Next.js → Spring Boot → PostgreSQL Gold views. A single pipeline command runs Bronze → Silver → Gold and records its result.

Azure: Azure Static Web Apps → Azure Container Apps API → PostgreSQL Flexible Server. A scheduled Container Apps Job runs the ETL and writes raw files to Blob Storage. Secrets are kept in Container Apps secrets or Key Vault.

Security boundary: the browser must call Spring Boot APIs only. It must never connect directly to PostgreSQL.

5. Phase 1: Stabilize the Gold Layer

  1. Document each Gold table, column, business meaning, and expected type.
  2. Define reporting views such as gold.stock_daily_summary, gold.stock_performance, gold.stock_technical_indicators, gold.market_overview, gold.top_gainers, and gold.top_losers.
  3. Replace unnecessary TEXT columns with numeric, date, and timestamp types.
  4. Add indexes on business_date, stock_code, ISIN, and hash_key.
  5. Define the grain of each table. For daily observations, the logical key will usually be ISIN + business_date; ISIN alone must not be unique because historical records intentionally repeat it. Keep hash_key as the row-level deduplication and idempotency key, including any additional fields required when more than one observation can exist for the same stock and date.
  6. Add elt_pipeline_orchestration.pipeline_runs with start time, end time, status, row counts, and error details.
  7. Add data-quality checks for duplicates according to the table grain, missing codes, invalid prices, missing dates, and unexpected row counts.
  8. Update project documentation so it reflects that Gold processing is implemented.

6. Phase 2: Build the Spring Boot Backend

Use Spring Web, Spring Data JDBC or jOOQ for reporting queries, PostgreSQL JDBC, Flyway, Spring Security, Bean Validation, Actuator, and OpenAPI.

For reporting-heavy endpoints, SQL projections or jOOQ are preferable to forcing analytical queries into complex JPA entities.

Initial API surface

  • GET /api/v1/market/overview
  • GET /api/v1/stocks?search=...
  • GET /api/v1/stocks/{stockCode}
  • GET /api/v1/stocks/{stockCode}/history
  • GET /api/v1/stocks/{stockCode}/indicators
  • GET /api/v1/market/gainers and /losers
  • GET /api/v1/pipeline/status

Use a read-only database user for reporting queries. Add authentication before making the application public.

7. Phase 3: Build the Next.js Frontend

Use Next.js App Router, TypeScript, TanStack Query, Zod, and Recharts or Apache ECharts. Start with a useful workflow instead of a broad feature set:

  1. Search for a stock.
  2. Show its latest Gold-layer data.
  3. Display historical price data.
  4. Display EMA and other technical indicators.
  5. Show average PnL and performance.
  6. Add watchlists after the read-only dashboard is stable.

Suggested pages: /dashboard, /stocks, /stocks/[stockCode], /market-movers, /watchlist, and /pipeline-status.

8. Phase 4: Local Containerized Development

Create a separate frontend and backend project folder, plus a root docker-compose.yml containing PostgreSQL, backend, frontend, and optionally the pipeline.

Create one entry point such as python -m ETL_Pipeline.run_daily_pipeline. It should run Bronze, Silver, Gold, quality checks, audit logging, and return a non-zero exit code on failure. This same container command should later be used by Azure Container Apps Jobs.

Because the current pipeline uses PySpark and Selenium, test its container footprint early. If daily files remain small, evaluate Polars or pandas and direct HTTP downloads to reduce Java, browser, memory, and startup requirements.

9. Phase 5: Azure Deployment

  1. Create one Azure resource group.
  2. Create PostgreSQL Flexible Server with the smallest suitable burstable tier.
  3. Create a Storage Account and Blob container for landing and archive files.
  4. Create a Container Apps environment.
  5. Deploy the Spring Boot API to Container Apps.
  6. Deploy the ETL image as a scheduled Container Apps Job.
  7. Deploy Next.js to Static Web Apps.
  8. Configure secrets, database networking, health checks, and logging.
  9. Add GitHub Actions for testing and deployment.
  10. Configure budget alerts and lifecycle rules for old raw files.

Schedule the job after the NSE source files are normally available rather than at midnight. Confirm the actual availability time during local testing.

10. Cost Controls

  • Keep one PostgreSQL server initially, with separate schemas for Bronze, Silver, Gold, orchestration, and application data.
  • Set Container Apps minimum replicas to zero where appropriate.
  • Use Static Web Apps for the frontend.
  • Use a small PostgreSQL burstable tier and scale down or stop non-production resources when not developing.
  • Use Blob lifecycle policies to delete temporary files and retain only required archives.
  • Avoid managed Airflow and Databricks until the workload needs them.
  • Use GitHub Actions instead of adding a separate CI/CD platform.
  • Set Azure budget alerts before deployment.

11. First Deliverable

Definition of done: one Gold reporting view, one Spring Boot endpoint, one Next.js stock page, one historical chart, one indicator display, Docker Compose local execution, and one repeatable daily pipeline command.

Once this vertical slice works locally, add market movers, watchlists, authentication, and additional analytics. Deploy to Azure only after the local flow is repeatable and the Gold contract is stable.
